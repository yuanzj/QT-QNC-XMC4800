# SDO完整提交只读计数取证

`--sdo-commit-trace`为默认关闭的测试观测开关，仅适用于正常场景9/INT64/模拟型号，不与位置或长度故障向量混合。它不改变SDO/PDO布局、工艺准入、接头反馈、控制或质量判定。关闭时HEX应与既有基线逐字节一致；实际构建结果须逐次核验，不能只根据宏定义推断。

```shell
python tools/build.py --gcc "<ARM-GCC>/bin/arm-none-eabi-gcc" --output build/sdo-trace --sdo-commit-trace
python tools/test_sdo_commit_trace.py --output evidence/sdo-trace-host
```

观测点为SSC完整`0x2030`写入准入、复制和长度/CRC提交后的`Pset_OnBufferReceived`回调，以及下一模型拍的解析/加载结果。计数的是完整工艺提交与模型加载，**不是邮箱分片数、TCP请求数或Flash写次数**。在UIO处被拒绝而没有到达完整SDO提交的请求不会增加此计数。

启用后ELF中提供`Simulation_SdoCommitDiagnostics`，2092字节，magic `0x53434E51`、version1。地址由该次ELF符号表取得，不能沿用别的构建地址。头部均为小端UINT32：magic、version、sequence、notifications、load_attempts、load_successes、load_failures、last_pset_no、last_length、last_mode、last_tick_ms，随后为256项received_by_pset及256项loaded_by_pset。按原始工艺号分别计数，可将其他工艺重装与受测工艺重复提交分开；失败、零长度与非法工艺号保留事实，不改成成功。

`notifications`只说明完整接收回调到达，`load_successes`才说明实际模型解析并装入成功。连续提交可先后覆盖待解析缓冲，不能仅凭通知计数声称全部加载成功；同时核对两组计数。`last_tick_ms`来自模型已经使用的单调毫秒，不是日历时间。计数生命周期为MCU本次启动，不持久化，不自动作为正式业务记录。

运行时没有对外写入或复位计数的命令。取证须区分停核、复位和SRAM保留：J-Link连接本板可能将PC停在复位入口，读到的是应用重新初始化前的保留RAM，不能称为非侵入在线读取。应同时保留同份ELF/固件SHA、PC/SP、原始RAM与完整调试器日志，读取后恢复明确的设备状态；任何初始化已覆盖或时间线不清的样本不能证明此前应用次数。

宿主回归使用实际适配入口：有效重复提交、非法模式、零长度与非法工艺号分别计数；开/关各6000拍的全部PDO输出严格相同，ASan/UBSan及非法组合拒绝通过。已纳入`tools/test_model_profiles.py`总门禁。宿主回归不代表真实总线取证或物理紧固质量合格，硬件结论以本轮独立证据为准。

## 2026-11-07实板增补

正常对照工艺和三个不同工艺号的首ACK丢失重发，均使用同一有效参数。C401/回读阶段的RAM计数为0；实际分别启动四颗后，完整接收及加载成功均为4、失败0，每个工艺号各1次，独立命令追踪恰好4次START。四颗均正常并保有完整曲线，证明此镜像的计数能在实际总线装载时递增。

该UIO路径先接收并保存工艺，只有启动才翻译并提交活动工艺到4800；仅选择验证已存工艺而不装载。C401/C402不能单独当成“4800已实际装入”的证据，第一次零计数不构成UIO故障。三组重发各两份相同SEQ/载荷、两份相同ACK，未提前产生装载或启动；后续各一次实际启动对应一次完整SDO提交/加载。此结论不测量UIO存储介质内部物理写次数。

两个RAM快照属于两次应用初始化区间，不能直接作跨复位差分；第二次阳性同时核对命令追踪与真实循环。启用计数后旧命令追踪结构的地址可能移动，两份地址都须从同次ELF解析，不能照抄历史固定地址。
